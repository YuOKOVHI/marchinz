# iPhone Safari「書類とデータ」膨張問題 — 現状と引き継ぎ

最終更新: 2026-08-07 / 対象: MarchinZ Switcher（映像ツール群）/ 本番 v2.3.0 (Beta)

**この問題はまだ解決していません。** 対策の半分は入っていますが、残り半分は
「サイト側のコードからは消せない」ことが実測で分かっています。
Codexで続きをやる人は、まずこの文書を最後まで読んでから手を動かしてください。

---

## 1. 症状

iPhoneの Safari が使う容量（設定 → 一般 → iPhoneストレージ → Safari → **書類とデータ**）が
数GB〜10GB超まで膨らみ、優さんの端末の空き容量を圧迫する。

**厄介なのは、iOSのサイト別「Webサイトデータ」一覧に出てこないこと。**
`marchinz.netlify.app` の行は 6.6MB のままなのに、本体の「書類とデータ」だけが
11GB を超えていた（2026-08-06 実機で確認）。だから「どのサイトが犯人か」を
iOSの画面からは特定できない。

---

## 2. 原因（実機で2種類の混合と判明）

2026-08-06 に優さんのiPhoneで、2段階に分けて切り分けた結果:

```
書類とデータの膨張 = ① 取り込みの一時コピー  +  ② OPFSの蓄積
                     （セッション性・消せない）  （永続・消せる）
```

### ① 取り込み時に WebKit が作る内部コピー ← **サイト側から消せない**

`<input type="file">` で動画を選ぶと、**WebKitがその動画を内部にコピーする**。
これはブラウザの実装であって、JavaScript からは触れない。

- **実測**: 素材3本（約3GB）を選んで分析中の画面で **10.29GB → 13.84GB（+3.55GB）**。
  書き出しは1回もしていない状態での増加
- **Safariを完全終了すると解放される**（13.95GB → 分析中17.5GB → 終了で復帰を実測）
- `clip.file` はページ再読み込みで消えるため、素材の再選択が必須（`tools/switcher/js/state.js`）。
  つまり**リロードのたびに再コピーが起きる**
- 優さんの判断で、**この件の案内はユーザーに出していない**

### ② OPFS（Origin Private File System）の蓄積 ← 対策済み・消せる

書き出した完成品と、分割書き出しのパーツが `mz-export` ディレクトリに積もっていた。

- **Safariを終了しても、iPhoneを再起動しても消えない**（実機で11.26GBを確認）
- これが「消せない11GB」の主体だった
- 積もった原因は2つ:
  - 書き出しを繰り返すと前回ぶんが手放されない
  - 別シーン・別設定で作り直す導線が `releaseOpfs` を呼ばない
  - 起動時掃除の「6時間据え置き窓」が、古くないファイルを守り続けた

## 3. 実施済みの対策（すべて本番投入済み）

| 版 | 内容 |
|---|---|
| v1.109.0 | 退出時にOPFSを即解放 / 旧ジョブのパーツを即掃除 / サイト保存量の診断表示 / `pagehide` での sweep |
| v1.109.1 | レビュー反映（ガードの穴・古い診断値・掃除の取りこぼし） |
| v1.110.2 | OPFS掃除の欠陥修正（他の修正と同梱） |
| v1.113.3 | **書き出し開始時に前回ぶんを必ず手放す** |
| v1.113.4 | **起動時掃除を2段構えへ**（下記） |
| v1.113.5 | 深い掃除の取りこぼしと消しすぎを両方塞ぐ（レビューP1×2） |
| v1.113.6 | **掃除が probe 待ちで止まる真因を修正**（下記） |

### 3-1. 起動時の「深い掃除」（`tools/switcher/js/exporter.js` の `opfsSweep`）

```
Web Locks を ifAvailable で取りにいく
  ├ "mz-export"        … どのタブも書き出していないか
  └ "mz-export-result" … 未保存の完成品を持つタブがいないか
        ↓
   両方取れた = 誰も使っていない
        ↓
   据え置き窓を無視して全消し
   （残すのは「今セッションの成果物」と「現行ジョブの再開パーツ6時間以内」だけ）

   片方でも取れなかった回 → 従来の6時間窓に落とす（保守的モード）
```

**効果**: Switcher を開いた瞬間に、溜まっていたOPFSが消える。

`mz-export-result` を条件に足した理由は、**書き出し完了〜「動画を保存」の間は
`mz-export` を誰も持っていない**ため。その隙に別タブを開くと、深い掃除が
未保存の完成品を消してしまっていた（v1.113.5 で発見・修正）。

### 3-2. 掃除を probe から切り離した（v1.113.6・3度目の対策）

以前は `probeOpfs()`（Workerを起こしてOPFSに実際に書けるか実測する）の
`.then()` に掃除をぶら下げていた。**probeOpfs にはタイムアウトが無く**、
iOS Safari で Worker が応答しないと `.then` が永遠に来ない
= **11GBを消したい当の起動で、掃除が1バイトも走らない**。

いまは両者を独立に走らせている（`tools/switcher/js/app.js` 86〜92行）。
掃除に必要なのは main thread の `getDirectory` / `entries` / `removeEntry` だけで、
Worker は要らない。

### 3-3. 縮小版（プロキシ）は持ち越さない

`pagehide` で `MC.proxy.disposeAll()` を呼ぶ。縮小版は引き当てに元の `File` が要るが、
`File` は再読み込みをまたいで生き残らないため、持ち越す意味がない。
取りこぼしても次回起動の掃除が据え置き窓を無視して必ず消す。

### 3-4. ユーザーが自分で消せる導線

`tools/switcher/js/ui.js` の `renderStorageNote()`（2575行付近）。
OPFSに **300MB以上**（`MC.ui.PURGE_MIN_BYTES = 300e6`）残っていると出る:

> **この端末に、作った動画のデータが ◯GB 残っています**
> 保存ずみなら消して大丈夫です。iPhoneの空き容量が戻ります。 　[消す]

「消す」は `MC.exporter.purgeAll()`。書き出し中は `busy` を返して拒否する。

### 3-5. 切り分け用の診断

`MC.exporter.estLine()`（`navigator.storage.estimate()` の結果）を
書き出し後の診断ログ（`#eoStats`）と `errorLog` に出している。

**読み方**: ここ（サイト枠）が小さいのに本体の「書類とデータ」が大きければ、
犯人は ①取り込みコピー。ここが大きければ ②OPFSの蓄積。

## 3-6. 新しく判明: 縮小版（プロキシ）の1時間据え置き ← 最有力の再発原因

2026-08-07 に優さんの指摘（「一度消せたのに、また残るようになったのはプロキシがきっかけか」）を
受けてコードと履歴を調べた結果、**時系列と機構の両方が合う経路**が見つかった。**未実機検証。**

```
08/06 19:48  v1.113.6  掃除がprobe待ちで止まる真因を修正 ← ここで「消せる」状態になった
08/06 20:39  v1.113.7  縮小版(プロキシ)を導入
             v1.113.8  フルレビュー反映                 ← ここで据え置きが入った
```

**v1.113.7 の時点では、プロキシは即消しだった**（安全側）:

```js
if (n.startsWith(MC.proxy.PREFIX)) {
  if (!MC.proxy._live.has(n)) { doomed.push(n); }   // 使用中でなければ即消す
  continue;
}
```

`_live` はメモリ上の Set なので、リロードすれば空。前セッションのプロキシは起動時に必ず消えた。

**v1.113.8 で 1時間の据え置きが追加された**:

```js
if (!MC.proxy._live.has(n) &&
    (mtime === null || now - mtime > MC.proxy.STALE_MS)) {   // MC.proxy.STALE_MS = 3600e3 = 1時間
```

入れた理由はコメントどおり「同一セッションの別タブが使っている最中に消すと、
そのタブの書き出しから縮小版を引き剥がす」で、心配としては正当。ただし副作用が2つある:

1. **プロキシは `continue` で抜けるので、深い掃除の「全部消す」を通らない。**
   他のファイルは深い掃除で容赦なく消えるのに、プロキシだけ1時間守られる
2. つまり「使った直後〜1時間以内に Switcher を開き直す」と縮小版は消えない。
   4K素材の縮小版なので小さくない

`mzprox_*.mp4` は書き出し物と**同じ `mz-export` ディレクトリ**に置かれる
（`MC.exporter.opfsRemove` が `OPFS_DIR` を見ていることで確認済み）。
だから「書類とデータ」に効く。

`opfsAudit` は全エントリを数えるので、画面の「◯GB残っています」にはプロキシも含まれる。
`purgeAll`（「消す」ボタン）は据え置きを全部無視するので、手動なら今でも消せる。

### この仮説の確かめ方（1時間あけるのが肝）

```
1. 「書類とデータ」の数値を控える
2. Switcherで素材を取り込む（書き出しはしなくてよい）
3. Safariを完全終了 → すぐ開き直す → 数値を見る      ← 減らないはず（据え置き中）
4. 1時間以上あけて、もう一度Switcherを開く → 数値を見る ← ここで減れば仮説が当たり
```

3で減って4でも減らないなら、犯人はプロキシではない。

### 2026-08-07: 管理者専用の実測診断を追加（v2.4.0）

「FHDだからプロキシは作っていない」と推定せず、**実際に作成処理へ入ったか・
成功したか・何bytesできたか**を記録する診断パネルを追加した。

- 管理者アカウントにだけ「Safari容量診断」を表示。一般ユーザーは入口も記録処理も動かない
- 動画・ファイル名は保存も送信もしない。素材1〜3の容量、実解像度、長さ、MIMEだけを端末内に記録
- プロキシは候補判定、予算見送り、作成開始、成功、失敗、破棄と実容量を別々に記録
- OPFSは `proxy / result / part / job / probe / other` に分け、掃除前後の件数・bytesを同時計測
- `navigator.storage.estimate()`、Web Locks、起動掃除が深/保守のどちらだったか、削除失敗を記録
- Worker probeが15秒返らない事実も記録する。ただし起動掃除はprobeと独立のまま維持
- iPhone設定画面の「書類とデータ」をGBで2〜3回入力すると、Safari差とOPFS差を比較し、
  OPFSで説明できない増加（取り込み内部コピー側）を分離する
- 診断中だけlocalStorageへ継続保存し、Safari終了・再訪をまたいで比較できる。
  「診断を終了・記録削除」で診断記録だけを消す

実機での最終分類は未確認。v2.4.0で本番検証を開始する。

### 2026-08-08: 実機結果と診断の再設計（v2.4.1・ローカル）

v2.4.0 の管理者実機で、FHD の QuickTime 素材3本を通常取り込み・分析した。

- 取り込み前: Safari「書類とデータ」5.81 GB
- 素材合計: 3,551,510,873 bytes（約3.55 GB）
- 取り込み・分析後: 9.36 GB（+3.55 GB）
- OPFS: 取り込み前後とも 0 B、起動時の深い掃除の実測解放も 0 B
- プロキシ作成・OPFS書き込みの記録なし
- Safariを完全終了して開き直した後も、iOS表示は 9.36 GB

この試行では、増分が選択素材の合計と一致し、OPFS・書き出し成果物・残存プロキシでは
説明できない。**Safari のファイル選択／取り込みに伴う内部領域が有力**だが、その正確な
保存先とWebアプリから解放可能かは未確認である。

同時に、初代の診断には次の判定ミスの余地が見つかった。

- 診断欄が素材選択用の画面内にあり、分析後には操作できなかった
- 日をまたいだ以前の数値まで同一試行の差分計算に混ざり得た
- `0.00 GB` の誤入力を差分の基準にできてしまった

v2.4.1 では、診断欄を全工程で見える位置へ移し、試行を開始し直すたびに過去記録を
履歴へ退避する。今回の差分計算は現在の試行だけを対象とし、`0.00 GB` は保存しても
差分計算には使わない。さらに次の段階を分離して比較できる。

1. **選択だけ**: 1本を選択直後に入力欄を解放し、動画解析・再生・プロキシ作成を開始しない
2. **通常取り込み・分析後**: 現行の実利用経路
3. **MarchinZ側の素材参照を外した後**: プレビュー、Object URL、アプリが握る `File` / `Video` 参照を外す
4. **Safari完全終了後**: Safariを終了して開き直した後のiOS表示

診断は管理者だけが使え、動画本体・ファイル名を保存・通信送信しない。素材の合計bytes、
解像度、長さ、MIME、OPFSの集計、Safari表示値だけを端末内に記録する。

実機手順（各段階のiOS「書類とデータ」を入力する）:

1. 「新しい試行を開始」→ 基準値を記録する
2. 「選択だけを試す」で、まず動画1本を選ぶ → 値を記録する
3. 通常の「動画を選ぶ」→ 分析完了後に値を記録する
4. 「MarchinZ側の素材参照を外す」→ 値を記録する
5. Safariを完全終了して開き直し、「Safariを開き直した」→ 値を記録する

素材参照解除で減らなければ、アプリが保持する参照が主因ではない。選択だけで増えれば
ファイルピッカー／WebKit経路、通常取り込み後だけで増えればMarchinZの処理経路を優先して
調べる。いずれも実機での確認前に断定しない。

### 2026-08-08: WebKit側に同一症状のバグ報告が見つかった（外部証拠）

https://bugs.webkit.org/show_bug.cgi?id=318572

| | |
|---|---|
| タイトル | Safari (iOS/iPadOS): every file passed through the Photos picker for `<input type="file">` permanently leaks its full size into Safari's "Documents & Data" storage |
| 報告 | 2026-07-03 / Takashi Kanemoto |
| 状態 | **NEW（未修正）** |
| 対象 | iOS 26 / iPadOS 18.6.2 / Safari 26（iPhone 16 Pro、iPad mini 6th） |
| Apple社内 | rdar://181340765 |
| 関連 | Bug 307321（大きな画像選択でサムネイル生成がページを固める） |

原文の要点:

- ファイルを選ぶたびに**準備されたファイルのバイトサイズぶん**ストレージが増える
- **`never reclaimed (survives force reboot)`** — 回収されず、強制再起動でも生き残る
- 最終的に **`Photos picker starts failing silently`**

再現手順も「基準値を控える → `accept="image/*,video/*"` のページで写真ライブラリから約1GB選ぶ →
待つ → タブを閉じてSafari終了 → 数値を見る」で、**こちらの診断と同じ形**。

**2026-08-08 の実機結果と完全に一致する。** +3.55GB は選択素材の合計と一致し、
OPFSは前後とも 0 B、プロキシ作成なし、Safari完全終了後も 9.36 GB のまま。
つまり **①取り込みの内部コピーが主犯で、しかもWebKit側の未修正バグ**という理解でよい。
サイト側のコードで消せないという結論は正しかった。

#### ただし2026-08-06の観測とは食い違う（回収条件は未確認）

| | |
|---|---|
| 2026-08-06 の観測 | Safari完全終了で解放された（13.95 → 分析中17.5 → 終了で復帰） |
| 2026-08-08 の観測 / バグ報告 | 終了しても戻らない（never reclaimed） |

同じ約1.19GBのQuickTime動画1本でpicker経路を分けて実機測定した。

| 経路 | Safari「書類とデータ」 | 増加 |
|---|---:|---:|
| 写真アプリ | 20.27GB → 21.46GB | 約1.19GB |
| ファイルアプリ | 21.46GB → 22.65GB | 約1.19GB |

どちらもOPFSは0Bで、選択した動画とほぼ同量増えた。したがって「ファイルアプリから選べば
回避できる」という仮説は反証された。現在の未確認点は、2026-08-06に一度だけ解放された条件である。

#### v2.8.1 のガードはこのバグと整合的

「基準値を記録する前は picker を開かせない」変更は、
**picker を開いた時点でコピーが起きうる**というこのバグの性質と合っている。
onchange 後に止めても容量は戻らないため、入口で止めるのが正しい。

さらにv2.8.1（ローカル）では、本人が「ツールを終了」を押した場合とMarchinZ内の別ページへ
移動した場合に、File、video要素のsrc、Object URL、proxy、解析/OPFS Worker、AudioContext、
書き出し結果、保存済み作業状態をまとめて解放する。通知確認・アプリ切替では動画を残す。
この完全解放でSafari本体の容量が減るかは、iPhone実機では未確認。

### 直すなら（案・未実装）

- 深い掃除（誰も使っていないと確認できた回）では、プロキシにも据え置きを効かせない。
  据え置きの目的は「同一セッションの別タブを守ること」であり、
  Web Locks が両方取れた時点で「別タブはいない」と分かっているため、両立できるはず
- ただし `mz-export` / `mz-export-result` の2ロックだけで
  「縮小版を使っている別タブ」まで捕まえられるかは要確認（プロキシ専用のロックが要るかもしれない）

### 未着手: 掃除のタイミング

掃除は **Switcher の起動時にしか走らない**。
MarchinZ の他ページ（TOP・大会動画など）を見ているだけでは走らない。
Switcher を開かずに容量だけ減らしたい、という要望が出たら設計変更が要ります。

## 5. 触るときの注意（過去に踏んだ地雷）

- **`opfsSweep` の入口を `opfsSupported()` に戻さない。**
  あれは Worker probe を含むので、probe が一時失敗した起動で掃除が全く走らなくなる。
  入口は `navigator.storage.getDirectory` の有無だけで判定する（v1.113.6 の教訓）
- **深い掃除の条件から `mz-export-result` を外さない。**
  外すと、書き出し完了〜保存の間に別タブを開いた人の**未保存の完成品が消える**
- **`purgeAll` は書き出し中に走らせない**（`busy` を返す実装を維持する）
- **診断の数値は「出す直前に測り直す」。** 古い値を握ったまま表示すると、
  対策の効果判定そのものが嘘になる
- 検証は **代入でなく操作で測る**。`navigator.storage.estimate()` を関数から
  呼んで満足せず、実際にSafariを終了→再訪して iOS の数値を見る
  （`repro-first` / `test-teeth` スキル参照）
