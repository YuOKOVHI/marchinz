## 2. 直近の指摘と、そこで見つかった真因

優さんから7件のURLが提示された（2026-08-12）。内訳:

- 1件 … すでに収録済み
- 1件 … 却下（他人の動画の**楽譜起こし版**。原本は収録済み）
- **5件 … 取りこぼし**

問題は、**その直前に同じ期間（米国時間8/10〜8/12）を全軸で探索したばかりで、
母集団15,463本を見ておきながら1件しか拾えていなかった**こと。
しかも5件中4件は**すでに収録実績のあるチャンネル**の新着だった。

### 真因：ネット取得の上限が、候補を無差別に切り捨てていた

```
flat_list（--flat-playlist）は 尺 も 公開日 も返さない（常に None / "NA"）
        ↓
meta_from_flat() は「dur is None なら諦める」門を持つ
        ↓
「タイトルだけで即採用」のショートカットが **実質一度も発動しない**
        ↓
全候補が judge_ids() のネット取得行き（当時の上限 200本）
        ↓
順番は チャンネルURLのアルファベット順 任せ
        ↓
既知チャンネルの新着だろうが何だろうが、201本目以降は「次回」送り
```

### 対処

1. `title_strong_signal()` を新設し、**タイトルだけでPOVと読めるものをネット取得の列の先頭へ回す**
   （採否そのものは変えない。尺の確認は必ずネットで行う）
2. 上限を **200 → 600** に引き上げ

### 効果（同じ期間・同じ条件で再スキャンして実測）

| | 修正前 | 修正後 |
|---|---|---|
| 母集団 | 15,463本 | 15,415本 |
| 見つかった候補 | **1本** | **5本** |

## 3. 正直な課題

### 3-1. ★最重要：上限600でも、まだ844本を切り捨てている

修正後スキャンの実測ログ:

```
[判定:一次] 15415本
  キャッシュ/題名 6894 / ネット要 8521（強い手掛かり 1444）
  ネット取得は先頭600本に制限（残り7921は次回、強い手掛かりは優先済み）
```

**「強い手掛かり」が 1444本あるのに、上限は 600本。**
つまり優先度付けをしてなお、**強い手掛かりのある候補が844本、今回も落ちている**。

「1件→5件に改善した」は事実だが、**問題が解決したわけではない**。
たまたま上位600本に入ったものが拾えただけで、
優さんが次にURLを提示すれば、また取りこぼしが出る可能性が高い。

### 3-2. `--since` が母集団を絞れていない（構造的欠陥）

`flat_list` が公開日を返さないため、日付の門が素通りになる:

```python
parse_upload_date("NA") → None
eligible_flat(...) → published is None or published >= since → True（常に通過）
```

結果、**「直近3日分を調べたい」のに母集団が15,415本**になる。
本来なら数十〜数百本のはずで、ここが絞れれば上限問題はほぼ消える。

### 3-3. 「次回に持ち越す」設計がキャッシュ前提

`fetch_meta` はディスクキャッシュ（現在 **16,098件**）に依存し、
上限を超えた分は「次回キャッシュが育ってから」という設計。
**日次1回の実行で追いつく保証がない**。
CI（GitHub Actions）はキャッシュを持ち越さないので、**毎回ゼロから**になる。

### 3-4. 自動採用の門が、実在する動画を落とす

`auto_safe` は 5〜20分に限定している。実測:

```
tWGGNcmJsJE  1218秒(20分18秒) → 自動採用されない「尺が範囲外」
fJAZAstbpBY  1207秒(20分07秒) → 同上
```

どちらも今回**手動で採用した本物**。Victory Run は複数曲を通すので20分超えは珍しくない。
日次の自動反映では、この種類が毎回Issue送りになる（＝人が見るまで入らない）。

### 3-5. 自己検知の仕組みが無い

今セッションで見つけた探索系の欠陥のうち、
**語順固定・SCVの楽器誤検出・ネット取得上限の3つは、優さんが具体的なURLを提示して初めて発覚**した。
スクリプト自身は「0件でした」と正常終了する。
**取りこぼしていることに自分で気づけない。**

### 3-6. その他

- **日次ワークフローは一度も成功していない**（修正はpush済み、今夜00:00 JSTが初回）
- **判断保留が61件**（大学バンド・WGI屋内団体・団体不明。範囲に含めるかの方針待ち）
- **未pushコミットが1件**（ed30509）

## 4. Cursorと協議したい論点

### 論点A: 母集団を先に絞るべきでは（§3-2 が本丸）

いまは「全部集めてから、ネット取得で絞る」。
これを「**集める時点で絞る**」に変えられないか。

- `flat_list` に公開日を持たせる方法はあるか
  （`--flat-playlist` を捨てる／`ytsearchdate` の順序を信頼して打ち切る／
  チャンネルの新着N件だけ見る、等）
- チャンネル再訪は「前回見たIDより新しいものだけ」で足りるのでは
  （**チャンネルごとの最終確認位置を台帳に持つ**）

### 論点B: 上限の設計そのもの

- 「強い手掛かり1444本」を全部見るには何分かかるのか（実測していない）
- 上限を撤廃し、代わりに**時間**で切るべきか（例: 30分で打ち切り）
- 打ち切ったとき、**次回は続きから**を保証する仕組み（カーソル/しおり）が要るのでは

### 論点C: 取りこぼしの自己検知（§3-5）

- 既知チャンネルの新着は「必ず全部judgeする」という**別枠**にできないか
  （横断検索の結果と同じ列に並べない）
- 「収録済み動画と同じチャンネル・同じ大会・同じ年で、CSVに無いもの」を
  定期的に洗い出す**照合バッチ**を作れないか

### 論点D: 自動採用の門（§3-4）

- 20分上限を延ばすか、「Victory Run を含むなら別枠」にするか
- 緩めるなら、混入18件の再発をどう防ぐか

## 6. 実装結果（Cursorとの設計合意を受けて）

§4 の論点A〜Dのうち、P0/P1/P4 を実装した（P2/P3は見送り。§7）。

### P0: 既知チャンネルの再訪を横断検索と別枠化＋チャンネルカーソル

- `pov_channel_cursors.json`（新規）: `{channel_url: {newest_seen_id, checked_at}}`
- `revisit_channel()`: カーソルがあれば `/videos` を新しい順で軽く読み
  (`REVISIT_SCAN_LIMIT=40`)、カーソルのIDに当たったら打ち切る。無ければ
  従来どおりフル走査(`CHANNEL_SCAN_LIMIT=80`)して初回のカーソルを確定する。
  カーソルに当たらなかった(投稿順が変わった等)ときは、見逃しを避けて
  読んだ分を全部返す(安全側に壊れる)。`--resync-channel` で強制フル再同期。
- `judge_ids(ids, label, cap=600)` に `cap` を追加。既知チャンネルの再訪
  (`revisit_ids`)は **`cap=None`(上限なし)で必ず完走**、横断検索
  (`other_ids`)だけ従来どおり `cap=600`。

### P1: 横断検索を「日次寄り」のときだけ浅くする

- `--search-results` 未指定時、`--year-from` を使っていない通常運転で
  `--since` が直近 **14日以内**なら `search_results=8`、それ以外は従来の `20`。
  （`NEAR_TERM_DAYS` / `NEAR_TERM_SEARCH_RESULTS`）

### P4: auto_safe の尺上限を拡張

- `AUTO_MAX_SEC`: 1200 → **1500**(25分、段語不要)
- 拡張帯 1500〜**2400**(40分): 既存の全条件(既知ch・POV語or楽器×cam・楽器・
  団体特定)に加え、題名に**大会の段語**(`STAGE_WORD`: victory run / finals /
  semifinals / prelims)が必須。無ければ不採用。
- 実際に自動採用から漏れていた本物2本(tWGGNcmJsJE 1218s / fJAZAstbpBY 1207s)
  が拡張後は通ることを回帰試験にした。

### 試験

63件 → **76件**。追加13件はすべて実データ・変異試験つき:
- `check_channel_cursor`: カーソル打ち切り/初回フル/見逃し時の安全側動作
- `check_judge_lane_separation`: 枠0がcap無し・枠1がcap=600であることをソース検証
- `auto_safe` の新境界(通常帯1500s境界・拡張帯1800s・拡張帯上限2401s・
  拡張帯+楽器なし・未知ch+拡張帯条件満たす〈18件再発防止の変異試験〉)

全ての新規試験は「わざと壊してFAILすることを確認 → 戻す」の変異試験で
歯があることを実測済み。

## 8. Cursorへ — P0実装後、日次ワークフローで見つかった副作用の報告

Cursorとの設計協議、ありがとうございました。P0(チャンネルカーソル)の実運転結果
(母集団99.99%減)は§7に書いたとおり狙い通りでしたが、**そのP0自体が日次CI
(GitHub Actions)を壊す副作用を持っていた**ので報告します。

### 何が起きたか

P0実装のコミット(71b6097)を反映した直後の日次実行(2026-08-12 15:58 UTC)で、
探索(ステップ6、10分間)は成功したのに、**「コミットして反映する」ステップが
3回リトライとも失敗**しました。優さんにGitHub Actionsの生ログを見てもらったところ:

```
error: cannot pull with rebase: You have unstaged changes.
error: Please commit or stash them.
```

### 真因

P0で新設した `pov_channel_cursors.json` は**git追跡対象**で、探索実行のたびに
自動更新されます。ところが `.github/workflows/videos-daily-update.yml` の
「変わったかを見る」「コミットして反映する」の両ステップの対象ファイルリストは
`大会動画リスト_POV.csv` / `data.json` / `data.inline.js` / `pov_ledger.json` /
`index.html` の5つのままで、**新設ファイルを追加し忘れていました**。

```
scoutがpov_channel_cursors.jsonを更新
  → git commitの対象に入っていないので未ステージのまま残る
  → git pull --rebase が「作業ツリーが汚れている」で拒否
  → 3回リトライとも同じ理由で失敗
```

これは他ジョブとの衝突(ワークフローのコメントが想定していた筋)ではなく、
単純にファイルリストの更新漏れでした。

### もう一つの副作用(これが実は本題)

pushが失敗する ⇒ カーソルの更新が**一度もoriginへ反映されない** ⇒
CIは毎回まっさらなcheckoutからやり直すので、**日次実行のたびにP0の効果
(母集団99.99%減)が発生せず、毎回「カーソル無しの初回」相当の重い全走査に
戻ってしまう**ことになります。push失敗そのものより、この方が実害が大きいです。

### 対処

両ステップの対象ファイルリストに `pov_channel_cursors.json` を追加(コミット
`b3720cc`)。他に影響する追跡ファイル(cf/CACHEはリポジトリ外、
`pov_candidates.tsv` は未追跡でrebaseをブロックしない)は無いことを
`scout_pov_videos.py` の書き込み先を全部洗って確認済みです。

### 学び

**新しく「scoutが自動で書くファイル」を追加するときは、必ずCIワークフローの
git add / diff 対象リストも同時に見直す**こと。ローカルでの動作確認だけでは
この種の欠陥は見えません(ローカルは`push_check.py`が別の仕組みで守っている
ため)。CIは毎回フレッシュなcheckoutなので、「ローカルでは問題ない」が
成立しません。
