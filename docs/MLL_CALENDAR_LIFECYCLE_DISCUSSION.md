## 1. 用語

| 用語 | Firestore / UI | 意味 |
|------|----------------|------|
| **イベント掲示** | `mll_calendar_events` | コミュニティ「演奏会等」タブに出る **みんな向けのカード**（開催日・名称・都道府県・募集対象など） |
| **参加スタイル（掲示上）** | `attendees/{uid}.style` | カレンダー上「誰がどう関わる予定か」の **日本語ラベル**（出演・観戦等） |
| **MarchinZ Log** | `mll_logs` | **個人プロフィール**に載る「自分のマーチング履歴」（関わり方 `role`、表示 `role_label`） |
| **募集対象** | `participation_format` | イベント作成時の「想定参加者」（観戦・出演・運営…）。**個人 Log とは別フィールド** |
| **あなたの関わり方** | `mll_logs.role` | 個人が選ぶ `watch` / `perform` / `team_staff` / `ops`（UI: 観戦・出演・チームスタッフ・運営） |

## 2. 現状仕様（as-is）

### 2.1 データモデル

**`mll_calendar_events/{eventId}`**（掲示）

- 主フィールド: `kind`, `date`, `title`, `venue_pref`, `event_url`, `participation_format`, `created_by`, `creator_display_name`, `creator_avatar_url`, `created_at`, `liked_by`
- **v0.4 追加（案 E）**: `status`（`active` | `trashed`、未設定は **active 扱い**）、`trashed_at`（ISO）、`trashed_by`（UID）、（任意）`original_created_by`（復元監査用）
- サブコレクション: `attendees/{uid}` → `{ style }`（日本語の参加スタイル）

**`mll_logs/{logId}`**（個人 Log）

- 主フィールド: `user_id`, `event_name`, `event_date`, `venue`, `role`, `role_label`, `note`, `ticket_url`, `official_url`, `visibility`, `created_at`, `liked_by`, …
- **`calendar_event_id`**（P0 以降・新規書き込みは付与。P1.5 スクリプトで既存データもバックフィル可）
- **`source`**: `event_register` | `calendar_attendance` | `legacy`（任意）

**弱い結合キー（実装で使っている一致条件）**

```text
matchKey = event_date + "|" + normalize(title) + "|" + venue_pref/venue
```

- プロフィールの「イベントへリンク」: `calMap`（当日のカレンダー一覧から組み立て）と上記キーで照合（`user-profile-page.js`）
- カレンダー統合（管理人）: 同一キーの `mll_logs` を統合先の日付・名称・会場に **書き換え**（`calendar-events.js` `rewriteMllLogsForMergedCalendar`）
- カレンダー「Logを残す」: 同一 `user_id` + `event_date` + `event_name` なら **1 件を merge**、なければ新規（`saveMyAttendance`）

### 2.2 作成経路（3 系統）

| 経路 | UI | 書き込み |
|------|-----|----------|
| **A. イベント入力フォーム** | 演奏会等 → イベント入力 → 登録する | `mll_logs` **新規** + `mll_calendar_events` **常に `.add()` 新規**（`mll.js`） |
| **B. カレンダー「MarchinZ Logを残す」** | 既存カード → ダイアログで関わり方 | `attendees` 更新 + 同一キーなら `mll_logs` merge、なければ新規（`calendar-events.js`） |
| **C. ローカル** | オフライン／失敗時 | `localStorage` `marchinz_mll_logs_v1`（Firestore 成功時も push） |

### 2.3 削除・更新

| 操作 | 掲示 | 個人 Log |
|------|------|----------|
| 作成者・管理人が **イベント削除**（**v0.4 / P1.8**） | **`status: trashed`**（ゴミ箱。物理削除しない）。`attendees` は維持可（復元用） | **作成者本人の Log のみ** 無条件で **物理削除**。他人の Log は **触らない** |
| 管理人 **イベント統合** | 統合元カード削除（または将来 `trashed`）、参加者を統合先へ移動 | 同一 matchKey / `calendar_event_id` の Log を統合先情報へ **更新** |
| 本人が Log 削除（イベント一覧側 UI） | — | `mll_logs` ドキュメント削除（`mll.js`） |
| **退会** | 掲示は **残す**（作成者表示は「退会ユーザー」） | 本人の `mll_logs` は **退会処理で削除**（`auth.js`） |

### 2.4 退会ユーザーと掲示の方針（確定済みの product 要件）

- 退会後も **過去に登録したイベントカードはサイトに残す**（マーチング文化の記録・他参加者の文脈のため）。
- 作成者名・アバターは **「退会ユーザー」** 表示（個人特定を抑える）。
- 退会ユーザー本人はログイン不可のため、新規 Log／編集は不可。

### 2.5 直近の技術修正（1.21.33）

- プロフィールの `mll_logs` 取得を **`user_id` 絞り込み**に変更（他者の非公開 Log が混ざるコレクション全体クエリが Firestore ルールで失敗していた問題）。
- 実装: `mll-role.js` の `queryMllLogsForUser` / `queryMllLogsForFeed`。

### 2.6 【重要・実装済み】運営による重複イベント「統合」と MarchinZ Log

**プロダクト要件（以前からの合意）**: 重複して載ったイベント掲示は、**運営（特権 UID）が「統合」**し、そのとき **MarchinZ Log も統合先の開催情報に揃える**。

**現状: 本番に実装済み**（協議ドキュメント初版では §2.3 表の 1 行にしか書いておらず、将来案の中心に見えにくかった。本節で明示する）。

| 項目 | 内容 |
|------|------|
| **誰が** | `isSiteAdmin()` ＝ 運営（`mll_privileged_uids` / 管理者メール。Firestore は `isPrivileged()`） |
| **UI** | 演奏会等カレンダー: 重複カードで **「統合元に指定」** → 別カードで **「ここへ統合」**（`calendar-events.js`） |
| **掲示** | 統合元 `mll_calendar_events` を削除。いいね・`attendees` を統合先へマージ |
| **Log** | `rewriteMllLogsForMergedCalendar`: 統合元と **同一 matchKey**（開催日・正規化タイトル・都道府県）の **全ユーザーの** `mll_logs` について、`event_date` / `event_name` / `venue` / `role` / `role_label` を統合先に **書き換え** |
| **失敗時** | Log 更新に失敗したら **掲示の統合も中止**（メッセージでルール・特権 UID を案内） |
| **ルール** | `isMllLogCalendarMergePatch()` — 特権ユーザーのみ、上記 5 フィールドのみ変更可（`firebase/firestore.rules`） |
| **文言** | 登録フォーム同意文: 「重複しているイベントは統合または削除いたします」（`index.html`） |

**「統合」の意味（Log について）**

- 現状は **ドキュメントのマージ（結合して 1 件にまとめる）ではない**。
- **統合元キーに一致した Log 行の「イベント情報フィールド」を統合先に寄せる**（ユーザー・`role` は維持。統合先の日付で `role_label` を再生成）。
- よって、同一ユーザーが統合元・統合先で **別 role の Log が複数ある**場合、統合後も **プロフィール上は複数行残り得る**（重複行の「統合削減」は未実装）。

**現状の限界（運営統合が効かない／弱いケース）**

| ケース | 結果 |
|--------|------|
| 統合元・統合先で **開催日・名称・会場が 1 文字でも違う** | matchKey 不一致 → **Log は 0 件更新**（掲示だけ統合される） |
| Log に `calendar_event_id` が無い（現状ほぼ全件） | 文字列キー頼み。表記ゆれ・誤登録でキーがずれると取りこぼし |
| 統合**後**に作成者が統合元カードだけ削除した | 統合前に Log 更新されていれば Log は統合先名義で残る。未統合のまま削除すると **孤立 Log** |
| 同一ユーザー・同一大会の **重複 Log 3 行** | 3 行とも同じ統合先名称に **更新される**が、**3 行のまま**（行数は減らない） |

**将来案への組み込み（必須要件として維持）**

- **案 B 以降**: `calendar_event_id` を導入したうえで、運営統合時は  
  - **(1)** `calendar_event_id == 統合元 eventId` の Log を統合先 ID・統合先 matchKey に更新（現行の書き換えの上位互換）  
  - **(2)** オプション: 同一 `user_id` + 統合先 `calendar_event_id` + 同一 `role` の Log は **1 件にマージ**（重複行削減）  
- **案 C**: 掲示は `archived` 化、統合は現行と同様に「正（canonical）」カードへ寄せる。
- 運営統合は **削除（§2.3）や P0 重複防止と対立しない**。重複掲示の**正規の整理手段**としてロードマップに残す。

## 3. 確認された課題

### 3.1 孤立 Log（orphan logs）

**現象**: プロフィールの MarchinZ Log にはイベント名・日付が表示されるが、**演奏会等の一覧には同じイベントが無い**。

**原因**:

1. カレンダー行だけ削除され、`mll_logs` は残る（`deleteEditedEvent` は `mll_calendar_events` のみ）。
2. 経路 A は **登録のたびに掲示カードも新規追加**するため、誤登録→削除を繰り返すと **Log だけが複数残りやすい**。
3. 経路 A と B で **重複防止ルールが非対称**（B は merge、A は毎回新規）。

**実例（2026-05-16 時点・ユーザー「おこち」）**

- プロフィール: 5 件（観戦 2・出演 1・運営 2 など）。
- うち 4 件は、当該日時の **カレンダー掲示と対応しない**（削除済み or 別 ID で統合済みと推測）。
- 同一大会名が **複数行**（例: SAITAMA 2026 が 3 行）→ 重複登録の痕跡。

### 3.2 ユーザー期待とのギャップ

| ユーザーが想像しがちな動き | 実際 |
|---------------------------|------|
| イベントを消したら Log も消える | Log は個人史として残る設計 |
| 同じ大会に再登録すると上書き | 経路 A では **新規 Log + 新規掲示** |
| プロフィールのリンクですぐイベント詳細 | 掲示が無いとリンク先が無い（名称だけ残る） |

### 3.3 退会との混同しやすい点

- **退会ユーザーの掲示を残す**要件と、**誤登録掲示を消す**要件は **両立可能**（掲示の `created_by` が退会 UID かどうかは別問題）。
- 問題の本質は「退会」ではなく **掲示と Log のライフサイクル未分離**。

### 3.4 セキュリティ・運用

- クライアントのみでの「削除時に他人の Log も消す」は **ルール設計と確認 UI が必須**。
- 2 アカウント運用期は Admin SDK スクリプトで孤立 Log の掃除は可能（`scripts/repair-mll-log-roles.mjs` と同様の運用）。

### 3.5 運営「統合」と Log のギャップ

- **統合機能はある**が、上記 §2.6 のとおり **matchKey 完全一致**に依存するため、重複カードの表記が少し違うと Log が追従しない。
- **Log 行の統合（同一ユーザーの重複行を 1 件化）**は未実装。運営が掲示を統合しても、プロフィールの行数が減らないことがある。
- 協議ドキュメント初版の案 A〜D は「統合」を **将来の中心要件として十分に書いていなかった**（本稿 §2.6・§5・§7 で補正）。

## 4. 設計原則（提案）

協議で合意したい **不変に近い方針**:

1. **掲示（コミュニティ）と個人 Log（プロフィール）は別ライフサイクル**
   - 掲示: みんなの「今見えるイベントボード」
   - Log: 本人の「マーチング人生の年表」（基本は削除しない）

2. **他人の Log をイベント削除で巻き込まない**
   - 作成者が誤って載せた掲示を消しても、他参加者が残した Log は保持。

3. **退会ユーザーの掲示は原則保持**
   - ソフト削除・アーカイブで一覧から隠す場合も、**監査・歴史用にデータは残す**方向。

4. **誤操作の取り消しは「本人に紐づく範囲」で明示的に**
   - 削除確認で「自分の Log も消す」を選べる、など。

5. **正規の参照は ID 結合へ寄せる**
   - 文字列 matchKey は表示・移行用に残しつつ、`calendar_event_id` を正とする。

6. **重複掲示の整理は「運営統合」を第一手段とする（既存機能を維持・強化）**
   - 作成者の単独削除だけに頼らず、**統合先 1 枚に寄せたうえで Log を追従**させる（§2.6）。
   - P1 以降は ID ベース統合と **Log 行のマージ（重複削減）**を実装する。

7. **UI の入力経路が違っても、保存ロジックは一本化する**（Gemini レビュー反映）
   - 経路 A / B で別実装のままにせず、掲示の検索・再利用・Log merge・`calendar_event_id` 付与は **共通関数**に寄せる。

## 5. 対策案

### 案 A: 最小 — 表示と重複防止のみ（実装コスト小）

| 項目 | 内容 |
|------|------|
| 重複防止 | 経路 A でも `user_id` + matchKey + `role` で既存 `mll_logs` を **merge**（B と同様） |
| 掲示 | 経路 A で同一 matchKey の `mll_calendar_events` が既にあれば **新規 `.add()` しない**（既存 ID を Log に紐づけ） |
| プロフィール | カレンダーに無い Log に **「掲示終了」** バッジ（削除・統合・過去イベントを区別しない簡易版でも可） |
| 削除 | 現状維持（孤立は手動 or スクリプト） |
| **運営統合** | **現状維持**（§2.6）。matchKey 改善は別途 |

**長所**: 退会・他人 Log に触れない。すぐ効く。運営統合は既に利用可。  
**短所**: 既存の孤立 Log は残る。削除連動は未解決。統合時の Log 行マージは未対応。

---

### 案 B: 推奨 — ID 紐づけ + 削除時の選択肢 + 運営統合の強化（中コスト）

**スキーマ追加（`mll_logs`）**

```text
calendar_event_id?: string   // 掲示 doc ID。無い場合は旧データ（matchKey のみ）
source: "event_register" | "calendar_attendance" | "legacy"
```

**イベント削除時（作成者・管理人）** — **v0.3 のチェックボックス案は v0.4 で廃止**（§13 案 E を正）

- ~~☑ 自分の MarchinZ Log も削除（選択式）~~ → **選択 UI なし**。削除時は **常に** 作成者 Log を物理削除（§13.2）。
- 掲示は **ゴミ箱（`trashed`）** へ。運営が復元可能（§13.3）。

**退会ユーザー掲示**: 変更なし（掲示 doc は残る。`status` は変更しない）。

**プロフィール**

- `calendar_event_id` で掲示の存在を確認。
- 無い / アーカイブ済み → 「掲示なし（個人記録のみ）」表示。イベント名・日付・ role は **Log 側フィールドを正**とする。

**マイグレーション**

- 既存 Log: `event_date` + `event_name` + `venue` でカレンダーを検索し、`calendar_event_id` を可能な限りバックフィル（Admin スクリプト）。
- 複数ヒット・0 ヒットは `source: "legacy"` のまま。

**運営統合の強化（§2.6 要件の延長）**

- 統合時の Log 対象: **`calendar_event_id == 統合元 eventId`** を優先（matchKey はフォールバック）。
- 確認ダイアログに **更新予定 Log 件数のプレビュー**（現状は統合後メッセージのみ）。
- 統合後: 同一 `user_id` + 統合先 `calendar_event_id` の Log を **1 ユーザーあたり 1 行にマージ**（v0.3 合意・優先ルールは §12）。
- 統合完了後 `marchinz-mll-updated` 発火でプロフィール再描画。

**長所**: 誤登録の掃除と個人史の保持を両立。**運営統合＋Log 追従を ID で確実化**できる。  
**短所**: ルール・UI・マイグレーションが必要。Log 行マージはポリシー設計（どちらの `created_at` を残すか）が必要。

### 案 C: ソフト削除（アーカイブ）— 掲示側中心（中〜大）

### 案 E: 運営ゴミ箱（ソフト削除）＋運営による引き継ぎ復元 — **正式採用（v0.4）**

大河内マネージャー・Gemini 協議（2026-05-17）で確定。**案 C の実用版**。

#### 13.1 ゴミ箱（ソフト削除）の基本

| 項目 | 仕様 |
|------|------|
| **トリガー** | 作成者または管理人が UI 上「削除」 |
| **掲示** | 物理 `delete` しない。`status: "trashed"`、`trashed_at`（ISO）、`trashed_by`（操作者 UID）を書き込む |
| **公開一覧・検索** | **`status == "active"`** のみ（**`status` 未設定は active 扱い**＝既存 doc 互換） |
| **誰が見えるか** | 一般ユーザー・作成者には **非表示**。**運営（特権 UID）のみ** ゴミ箱一覧（**P2 UI**） |
| **attendees** | P1.8 では **削除しない**（復元時に参加スタイルを残す。容量が問題になれば P2 以降で整理） |

#### 13.2 削除時の Log 挙動（P1.8 で実装・**チェックボックス廃止**）

作成者・管理人がイベントを削除したとき:

| 対象 | 挙動 |
|------|------|
| **イベント掲示** | `trashed`（§13.1） |
| **作成者本人の MarchinZ Log** | **`calendar_event_id` 一致かつ `user_id == 操作者`** の doc を **無条件で物理削除**（ユーザーに選択させない） |
| **他人の Log** | **一切触らない**（孤立・「掲示なし」は P1.5b で表示） |

**設計意図**: 「掲示を間違えて消した」は運営がゴミ箱から復元できるが、「自分の参加記録を残したくない」は削除操作で本人 Log だけ確実に消す。他人の年表は侵害しない。

**v0.3 → v0.4 の変更点**: P1 で入れた **「自分の Log も削除」チェックボックス（デフォルト ON）** は **UI ごと撤廃**。挙動は **常に ON** に固定。

#### 13.3 運営による復元（引き継ぎ）— **P2 UI**

| 項目 | 仕様 |
|------|------|
| **誰が** | 運営（`isPrivileged()` / `isSiteAdmin()`）のみ |
| **操作** | ゴミ箱一覧から「復元」 |
| **掲示** | `status: "active"` に戻す。`trashed_at` / `trashed_by` は空文字または削除（実装で統一） |
| **作成者の引き継ぎ** | **`created_by` を運営 UID に上書き**。`creator_display_name` / `creator_avatar_url` を運営プロフィールに更新 |
| **監査** | （推奨）`original_created_by` に復元前の `created_by` を保存。`restored_at` / `restored_by` を任意で記録 |
| **Log** | 復元時点で **他人の Log は既に存在**（削除時に触っていない）。作成者 Log は削除済みのため **復元しない**（本人が再度「Logを残す」で再登録） |

#### 13.4 退会・物理削除との関係

| 操作 | 掲示 | Log |
|------|------|-----|
| **イベント削除（作成者）** | ゴミ箱 | 作成者 Log のみ物理削除 |
| **退会** | 掲示は残す（退会ユーザー表示） | 本人 Log は退会処理で物理削除（§2.4・変更なし） |
| **運営の永久削除（将来）** | ゴミ箱から物理 `delete`（P2 以降で検討） | 方針は別途（カスケードは No-Go のまま） |

#### 13.5 P0 / 統合との整合

- **P0**: `active` な掲示のみ matchKey 検索対象。`trashed` は新規登録時に **別イベントとして再作成可**。
- **運営統合**: 統合元は引き続き **物理削除** または将来 `trashed` 化を検討（v0.4 では現行の物理削除を維持可）。

### 案 D: サーバー側カスケード（Cloud Functions）（大）

- `onDelete(mll_calendar_events)` で、ポリシーに従い `mll_logs` / `attendees` を整理。
- ポリシー例: `removed_by_creator` かつ `only_creator_logs` フラグ時のみ creator の Log 削除。

**長所**: クライアント改ざんに強い。  
**短所**: 課金・デプロイ・テストコスト。現状 Netlify 静的 SPA 中心の構成から一段複雑化。

## 12. 合意したデータルール（v0.3）

### 12.1 Log 行マージの優先ルール（統合時・Admin スクリプト共通）

同一 `user_id` + 同一 `calendar_event_id`（バックフィル前は同一 matchKey）で複数 `mll_logs` があるとき、**1 件を残し他を削除**。

## 付録 A — Gemini レビュー全文（2026-05-16）

以下、外部 AI（Gemini）からのレビュー結果を **改変なく** 保存する。

---

プロダクト設計のレビュアーとして、MarchinZの現状仕様と課題を拝見しました。個人史（Log）と公共の掲示板（イベント）という2つのライフサイクルが交差する、非常に面白く、かつ設計が難しい部分に直面されていますね。

現状の「孤立Log」や「重複行」の根本原因は明確で、「文字列ベースの紐付け（matchKey）の脆さ」と「経路A（フォーム）が常に新規イベントを生成する仕様」にあります。

以下、レビュー結果と推奨案を整理しました。

### 1. エグゼクティブサマリー（5行以内）

- 案B（IDベースの紐付け）への移行を最優先のゴールとします。文字列（matchKey）依存は限界です。
- 最大の発生源である「経路Aの無条件な新規作成」を止め、「検索→既存があればLog追加、なければ新規作成」のUXへ改修が必要です。
- 運営統合時はフィールドの上書きだけでなく、同一ユーザーの重複Logの「行マージ（1件化）」が必須です。
- クラウド側のトリガー（案D）は現状不要で、クライアント側と管理スクリプトの運用で十分カバーできます。

### 2. 推奨する最終形

- **データモデル**: mll_logs は必ず calendar_event_id を保持する。正規参照はID、文字列情報は非正規化（表示用キャッシュ）として扱う。
- **削除の挙動**: イベント作成者がイベントを消す際、「自分のLogも削除する」はデフォルトONで明示。他人のLogは触らない（孤立Logになるが許容）。
- **運営統合**: 統合元のIDを持つ全LogのIDを統合先に書き換え、同一ユーザー・同一IDのLogが複数発生した場合は「最も関与度の高いRole」を残して1件にマージする。
- **退会処理**: 掲示板（イベントカード）やコメントは「退会ユーザー」として保持し、個人の活動履歴（mll_logs）は完全に物理削除する（SNSの標準的規約に準拠）。

### 3. フェーズ別の Go / No-Go と具体策

段階的にリリースし、ユーザー（現状はオーナー）のデータ破壊を防ぎます。

**【Go】P0：出血を止める（案A改 + ID付与準備）**

- 対応: 経路A（フォーム）の保存ロジック修正。すでに同日・同名のイベントが存在する場合、新規カードを作らず既存カードへのLog追加（経路Bと同じ挙動）に倒す。
- 対応: mll_logs の新規作成時に calendar_event_id を必ず書き込むようにする。

**【Go】P1：構造の強靭化（案Bの完全適用）**

- 対応: 運営統合ツール（calendar-events.js）の改修。matchKeyではなく calendar_event_id ベースでLogを更新する。
- 対応: 統合時の「同一ユーザーLogの行マージ」実装。
- 対応: 削除時の「自分のLogも削除」チェックボックス（デフォルトON）実装。

**【Go】P1.5：表示の最適化と掃除**

- 対応: プロフィール表示時、calendar_event_id に紐づくイベントが存在しない（孤立Log）場合、「イベント詳細不明」などのバッジ付きで表示する（個人の年表としては事実だから残す）。
- 対応: Node.jsのAdminスクリプトで、過去のmatchKey依存Logに正しい calendar_event_id を埋め込む（ユーザーが2名のみの今がラストチャンスです）。

**【No-Go】P2：案C（ソフト削除）、案D（Cloud Functions）**

現状のトラフィックと規模ではオーバースペックであり、Firestoreのクエリ複雑化を招くため見送りを推奨します。

### 4. 依頼事項（6.1）への個別回答

**設計原則は妥当か？**

妥当です。「掲示とLogは別ライフサイクル」という原則が最も重要です。追加するなら「UIの入力（経路）が違っても、最終的なデータ生成ロジックは必ず1つの関数（API）を通す」という原則を設けてください。

**案Aだけで足りる期間はあるか？**

ほぼありません。P0として「重複の発生を止める」のは数日以内の暫定対応とし、すぐにID化（案B）に進むべきです。

**同一ユーザーのLog行マージの優先ルールは？**

マージ必須です。優先ルールは「関与度の強さ」と「最新性」です。  
ops (運営) > perform (出演) > team_staff (スタッフ) > watch (観戦) の順で強いRoleを残し、同じRoleなら updated_at が新しい方の備考（note）等を正とします。

**イベント削除時、「自分のLogも削除」のデフォルトは？**

デフォルトONを推奨します。自分で作ったイベントを消すということは「間違えた」か「やめた」かのどちらかであり、個人の履歴からも消したいのが自然な心理です。

**matchKey を残すか、calendar_event_id 一本化か。**

ID一本化が必須です。matchKeyは表記ゆれ（「第30回」と「第３０回」など）で容易に崩壊します。既存LogへのIDバックフィルスクリプトを書いて一気に移行してください。

**プロフィールの掲示なし（孤立）Log の扱いは？**

バッジ付きで表示（リンクなし）を推奨します。イベントカードが消えても「私があの日、あの大会に出た」という個人の事実は消えないため、マーチング年表としての価値を優先します。

**退会後も掲示にイベント名が残ることと規約の整合。**

法的・規約的に問題ありません。「ユーザーが公開目的で投稿したコンテンツ（掲示板トピックやイベント情報）は、退会後も匿名化して保持される場合がある」旨を利用規約に1文入れておけば、一般的なCGM（食べログやWikipedia等）と同じ扱いです。

### 5. 見落としている論点（重大なリスク）

**UXの根本課題：「既存イベントを探す」動線が弱い**

経路A（フォーム）で重複イベントが大量発生する最大の理由は、ユーザーが「すでに誰かがその大会を登録しているか」を確認せずにフォームを書き始めるからです。  
フォームの最初に「大会名」を入力させ、既存の mll_calendar_events をインクリメンタル検索（サジェスト）して表示するUIが必要です。  
「あ、もうこの大会登録されてる！じゃあ『Logを残す』ボタンを押そう」とユーザー自身に気づかせるUIにしないと、裏側のシステムでどれだけ重複排除を頑張ってもイタチごっこになります。

まずは、ユーザー2名の特権を活かして、Node.jsスクリプトによる「全mll_logsへの calendar_event_id 付与と重複行の物理削除（マージ）」という大手術（P1.5の事前実施）を行うことを強くお勧めします。

*付録 A 終わり*
